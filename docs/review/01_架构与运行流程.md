## 2. 整个项目在做什么

客户端通过 TCP 连接发送 HTTP 字节。服务器逐步把字节解析成 HttpRequest，根据配置决定如何处理，再把结果转换成 HTTP 字节，通过同一条 TCP 连接发送回去。

这里有三个需要分开的动作：接收字节、理解请求、执行请求。recv 成功不代表 HTTP 请求完整；HTTP 请求完整也不代表目标文件存在；响应已生成也不代表已经发送完。

```text
启动阶段（通常只执行一次）
main → ConfigParser → Tokenizer / TokenStream → ServerConfig
     → ConfigValidator → Server → 创建监听 socket

运行阶段（重复执行）
poll → 接受连接 / 读取客户端 / 写给客户端 / CGI 管道读写
        ↓
Client 保存数据和 RequestState
        ↓
RequestParser 解析 → RequestHandler 检查和路由
        ↓                         ↓
普通文件响应                   CgiHandler 子进程
        └───────────┬─────────────┘
                    ↓
            Client._writeBuffer → send
```

## 3. 全部自定义类型，以及它们保存什么

共有 15 个自定义 class、2 个 struct、4 个 enum。没有自定义继承树，也没有 virtual 多态；主要关系是“包含”“引用”和“调用”。Utils 虽然只有静态方法，语法上仍是 class。

| 类型 | 保存的数据 / 责任 | 生命周期与关系 |
| --- | --- | --- |
| Server | 所有配置、监听 fd、客户端表、poll 列表、CGI 任务表 | main 中创建，run 返回后析构；调度中心 |
| Client | fd、读写字符串、发送偏移、serverIndex、端口、客户端地址、服务器地址、活动时间、RequestState | 一个 TCP 连接对应一个 Client；Server 的 map 按值保存 |
| RequestState（struct） | HttpRequest、解析阶段、读取位置 pos、Content-Length、当前 chunk 大小、keepAlive | Client 内部成员；每个请求完成并发送后重置 |
| HttpRequest | method、解码后的 path、query、version、headers、body、解析状态码 | RequestState 内部成员；RequestParser 是 friend，可直接修改私有字段 |
| RequestParser | 没有持久成员；只有解析方法 | 处理时临时创建；真正的解析进度在 RequestState 中 |
| RequestHandler | const ServerConfig 引用 | 每次处理时临时创建，借用 Server 内的配置，不拥有配置 |
| MultipartPart（struct） | headers、表单字段 name、filename、data | 一次 multipart 解析的局部 vector 内，处理结束销毁 |
| HttpResponse | 状态码、响应头 map、响应体 | 普通响应的局部对象；getResponse 序列化后交给 Client |
| CgiHandler | 客户端 fd、子进程 PID、管道 fd、输入输出状态、正文缓冲、环境变量、退出状态、活动时间 | 每次 CGI 创建一个；Server 持有指针并负责删除 |
| ConfigParser | 没有持久成员 | 启动时读取配置，构建 vector<ServerConfig> |
| ConfigValidator | 没有持久成员 | 启动时验证配置对象的语义与一致性 |
| Tokenizer | 没有持久成员 | 将配置文本拆成 token |
| TokenStream | token 数组副本、当前下标 | 为 ConfigParser 提供顺序读取接口 |
| ServerConfig | listens、root、index、body 上限、error_pages、locations | 一个 server 块对应一个对象；Server 持有配置副本 |
| LocationConfig | path、root、methods、autoindex、upload_store、重定向码与 URL、index、CGI 映射、body 上限及是否显式设置 | ServerConfig 中按值保存 |
| ListenConfig | host、port | ServerConfig.listens 中按值保存；表示一个监听配置 |
| Utils | 没有对象状态 | 提供 trim、toLower、sizetToString、decodeUri 静态函数 |
| HttpStatus（enum） | 200、201；301、302、303、307、308；400、403、404、405、413、414、431；500、501、505 | HTTP 状态码常量，不是类 |
| ParseStage（enum） | REQUEST_LINE、HEADERS、CONTENT_BODY、CHUNK_SIZE、CHUNK_DATA、DONE（源码带 STAGE_ 前缀） | 表示正在解析哪个阶段 |
| StageResult（enum） | STAGE_OK、STAGE_INCOMPLETE、STAGE_ERROR | 单个解析阶段的结果 |
| ParseResult（enum） | PARSE_COMPLETE、PARSE_INCOMPLETE、PARSE_ERROR | 整个请求解析的结果 |

系统提供的结构另有 pollfd、addrinfo、sockaddr、sockaddr_in、stat、dirent；DIR 是目录流类型，详见知识点的系统接口表。DEBUG_LOG 是宏，g_running 是全局变量，都不是类。

## 4. 对象关系与资源所有权

```text
main
└─ Server
   ├─ vector<ServerConfig> _configs
   │  ├─ vector<ListenConfig> listens
   │  └─ vector<LocationConfig> locations
   ├─ map<int, Client> _clients
   │  └─ Client → RequestState → HttpRequest
   ├─ vector<pollfd> _pollFds（事件登记表，不负责自动 close）
   ├─ vector<CgiHandler*> _cgiHandlers（同一批 CGI 对象的生命周期管理）
   └─ map<int, CgiHandler*> _cgiFds（用管道 fd 快速找到这些对象）

RequestHandler ──借用──> 一个 ServerConfig
RequestParser ──修改──> 一个 RequestState / HttpRequest
CgiHandler ──管理──> 子进程 + 两个父进程侧管道端
```

同一个 CgiHandler 可以在 _cgiFds 中出现两次，因为它有输入、输出两个 fd；这不是两个 CGI。真正删除对象时只能 delete 一次。

Client 析构函数是空的。虽然 Client 保存 fd 数字，关闭 socket 的责任在 Server。复制 Client 会复制 fd 数字，并不会创建新的内核连接。

RequestHandler 保存引用，引用对应的 ServerConfig 必须比它活得久。当前 Server 的 _configs 提供这个寿命。getLocation 返回的指针指向配置 vector 中的元素，也不是 new 出来的，不能 delete。

Server 的析构流程是先 delete CGI 对象，再遍历 poll 表 close fd。理解时要注意：CgiHandler 析构也会关闭自己的管道，因此不能把当前析构描述为已经严格保证“每个 fd 只关闭一次”；这是现有代码的清理边界，见第 13 节。

## 5. 启动阶段：从配置文本到监听 socket

### 5.1 main 的完整顺序

1. 检查 argc 必须等于 2；错误时输出用法并返回 1。
2. 注册 SIGINT 回调 handleSignal，忽略 SIGPIPE。
3. ConfigParser::parse 读配置并返回 servers。
4. ConfigValidator::validate 验证 servers。
5. 创建 Server，复制 servers 到 _configs。
6. 调用 Server::run，进入长期运行的循环。
7. Ctrl-C 使 g_running 变成 0；循环结束后局部对象自动析构。
8. 异常传到 main 的 catch 时输出错误，返回 1；正常结束返回 0。

handleSignal 由系统交付信号时触发，并不是 main 顺序执行时直接调用。它只修改退出标志，不在回调里销毁服务器。

### 5.2 配置解析和配置验证分别做什么

```text
ConfigParser::parse
  ├─ ifstream 读取整个文件
  ├─ Tokenizer::tokenize
  ├─ TokenStream(tokens)
  └─ 循环 parseServer
      ├─ parseListen / parseRoot / parseIndex / parseErrorPage
      ├─ parseServerClientMaxBodySize
      ├─ parseLocation
      │   └─ 各 location 指令的 parseXXX
      └─ ServerConfig::applyDefaultsToLocations

ConfigValidator::validate
  └─ validateServer
      ├─ validateListens / validateRoot / validateIndex
      ├─ validateErrorPages
      └─ validateLocations → validateLocation
          └─ validateMethods / validateRedirect / validateUpload / validateCgi
```

Tokenizer 认识空白、# 注释、分号和花括号。TokenStream::match 成功时已经消耗关键字；下层 parseRoot 等函数从“值”开始读取。expect 表示当前位置必须匹配，失败就抛异常。

ConfigParser 检查语法、数值范围和重复指令；ConfigValidator 检查对象组合是否合理，例如 upload_store 必须配 POST。当前部分规则在两个层次重复验证，不能理解为 Validator 会替代所有 parser 检查。

root 和 index 的继承在 applyDefaultsToLocations 中完成：location 空值会填入 server 值。body 上限则没有在这里复制，它由请求阶段根据 hasClientMaxBodySize 动态选取。0 表示不限制，因此必须用单独的 bool 区分“没写”和“显式写 0”。

### 5.3 创建监听端点

run 先检查所有 server 之间是否存在完全相同的 host:port，再逐个 setupListenSocket：

```text
socket → setsockopt(SO_REUSEADDR) → setNonBlocking
       → getaddrinfo → bind → freeaddrinfo → listen
       → 加入 _listenFds 和 _pollFds
```

_listenServerMap 保存“监听 fd → server 配置下标”，_listenPortMap 保存“监听 fd → 端口”。某个端点创建失败会跳过；所有端点都失败才抛异常。不同 IP 使用相同端口与同一 IP:port 使用 Host 虚拟主机是两回事，当前实现的是前者。

## 6. poll 主循环：为什么一个线程能处理多个连接

每轮先检查 CGI 子进程、CGI 超时、客户端超时，再 poll 最多等待 100 毫秒。poll 返回后逐个查看 revents。

| fd 类别 / 事件 | 入口 | 作用 |
| --- | --- | --- |
| 监听 socket + POLLIN | acceptClient | 接受一个连接并建立 Client |
| 客户端 + POLLIN | handleRead | recv 一次，再 processRequest |
| 客户端 + POLLOUT | handleWrite | send 一次，从上次发送偏移继续 |
| CGI 输出管道 + POLLIN | handleCgiRead | 从 CGI stdout 读取一批字节 |
| CGI 输入管道 + POLLOUT | handleCgiWrite | 向 CGI stdin 写入一批正文 |
| CGI + POLLHUP | handleCgiHangup | 输出端继续读取剩余数据；输入端关闭 |
| CGI + POLLERR / POLLNVAL | handleCgiError | 标记失败、杀子进程并结束任务 |
| 客户端错误 / 挂断 | removeClient | 关闭连接、移除对象及相关 CGI |
| 监听 socket 错误 | throw | 当前 run 退出，交给 main 报错 |

events 是服务器“想等什么”，revents 是 poll“本次发现了什么”。只有有响应待发才订阅 POLLOUT，避免不断被可写事件唤醒。

等待 CGI 时，客户端 events 设为 0，暂停客户端正常收发；不代表 close，也不保证收不到错误或挂断通知。此阶段 client 超时检查跳过它，CGI 超时单独管理；CGI 完成后重新切换为 POLLOUT。

循环里的 i 通过引用传递。删除当前 vector 元素后，后一个元素会左移到当前 i，因此经常需要“不自增”；没有删除时由对应分支递增。不能机械地给每个分支都加 ++i。

非阻塞只是 socket/管道 I/O 不会因等待数据长时间卡住。普通文件读取、文件写入、目录遍历、字符串复制，以及 killChild 中的阻塞 waitpid 仍可能占用事件循环时间。

## 7. 从 recv 到 HttpRequest：状态机

acceptClient 调用 accept，然后设置新 fd 非阻塞，取得配置下标、端口和地址，创建 Client 并订阅 POLLIN。

handleRead 每次最多 recv 4096 字节：负值关闭连接；0 表示对端结束发送，当前实现关闭连接；正值追加进 Client._readBuffer 并更新时间，然后调用 processRequest。

### 7.1 processRequest 的判断顺序

```text
查 Client 和 ServerConfig
  → parseClientRequest
    ├─ INCOMPLETE：等待下一次 POLLIN
    ├─ ERROR：生成错误响应，keepAlive=false
    └─ COMPLETE：consumeReadBuffer(state.pos)，state.pos=0
  → 非 GET/POST/DELETE 时设置 keepAlive=false
  → preCheck（true 表示已经生成响应，要提前结束）
  → tryStartCgi（true 表示已接管，包括启动失败已排队错误响应）
  → handleResolved（普通 GET/POST/DELETE）
  → queueResponse → 等 POLLOUT
```

两个 bool 的意思尤其容易读反：preCheck 返回 true 是“已经拦截/处理”；tryStartCgi 返回 true 是“该请求已被 CGI 分支接管”，不是“CGI 一定成功执行完成”。

### 7.2 为什么先解析 request line

请求行中有路径。parseClientRequest 先 parseRequestLineStage，得到并解码路径，找到 location，然后选 body 上限；再让 parser.parse 继续解析 header 和 body。这样 location 可以比 server 的 body 限制更大、更小，或设置为不限。

RequestParser 本身没有状态成员，所以每次重新创建不会丢进度。state.stage、state.pos 和已经解析的 HttpRequest 都保存在 Client 中。

### 7.3 状态转移

```text
REQUEST_LINE → HEADERS
                 ├─ 无正文长度信息 → DONE
                 ├─ Content-Length → CONTENT_BODY → DONE
                 └─ chunked → CHUNK_SIZE
                                ├─ 非零 → CHUNK_DATA → CHUNK_SIZE
                                └─ 0 + 结束空行 → DONE

任何阶段：数据不足 → INCOMPLETE，保留进度
任何阶段：语法/限制错误 → ERROR，记录 HTTP 错误码
```

请求行最多 8192 字节（含 CRLF）；header 块最多 32768 字节（含末尾 CRLFCRLF）；chunk 大小行最多 1024 字节（含 CRLF）。这些是本项目的限制值。

请求行先分离 query 再 decodeUri(path)。query 保留原字符串；path 中合法的 %HH 解码一次，%00 被拒绝。Host 必须存在且非空；Host、Content-Length、Transfer-Encoding 不允许重复；Content-Length 与 Transfer-Encoding 同时出现被拒绝。

当前固定长度正文要等整段数据到齐，才从 readBuffer assign 到 request._body。chunked 是逐块解析并拼接，但 readBuffer 到整个请求完成才消费。因此“增量解析”不等于“流式上传”。

## 8. 普通资源处理：GET、POST、DELETE

### 8.1 三层检查并不重复

| 阶段 | 检查对象 | 例子 |
| --- | --- | --- |
| 启动配置检查 | 配置文件和配置对象 | methods 拼写、重复 root、上传是否允许 POST |
| HTTP 解析检查 | 收到的字节是否组成合法请求 | Host 缺失、长度非法、header 太长 |
| 请求业务检查 | 这一次请求是否允许、资源是否可用 | 方法被禁止、路径含 ..、文件不存在 |

文件可能在服务器启动后被删除，客户端可能在任何时候发送非法请求，所以运行时检查不能被启动验证替代。

### 8.2 location 与实际路径

findLocation 按路径边界进行最长匹配，因此 /upload 不会普通地匹配 /uploads。还专门处理 requestPath + '/' 等于 locationPath 的情况。

当前 buildPath 规则类似“替换 location 前缀”：location /images 配 root ./assets 时，请求 /images/a.png → ./assets/a.png。没有 location 时用 server root + requestPath。location / 是特例，保留整个 requestPath。

preCheck 依次检查父目录穿越、为以 / 结尾的 location 补斜杠重定向、方法许可、显式 return。HTTP 重定向会发送响应，让客户端另发请求；服务器不是修改路径后继续内部执行。

### 8.3 GET

handleResolved → handleGet → buildPath → stat。

普通文件：ifstream 读入内存 → getMimeType → HttpResponse 200。

目录：缺少 URL 尾斜杠时返回 301，并对路径编码、保留 query；否则先查 index。index 存在且为普通文件就读取；不存在时，若 autoindex 开启则生成列表，否则 404。没有可用 index 且 autoindex 关闭的相关分支可返回 403。

autoindexResponse → generateAutoindex → opendir / readdir / stat / closedir。页面显示文字调用 htmlEscape，链接路径调用 urlEncodePath，两者保护的语法环境不同。

### 8.4 POST

如果先匹配到 CGI 扩展名，请求已经由 CGI 分支接管，不会进入普通 handlePost。

multipart/form-data：getBoundary → parseMultipart → 遍历 MultipartPart → isSafeFilename → upload_store + filename → writeFile。新建过文件则返回 201，只有覆盖则返回 200。

普通正文：buildPath 得到目标文件，writeFile 写入原始正文；新建 201、覆盖 200。这个分支不使用 upload_store。使用 /upload/test.txt 测试普通正文时，不能据此认定它会写到 ./uploads/test.txt。

当前 multipart 会在任何写入前先完成语法解析，但文件名合法性在写入循环中逐项检查，因此不是多文件上传事务：后一个文件名出错时，前一个文件可能已经写入。

### 8.5 DELETE 与错误响应

handleDelete → buildPath → stat 确认普通文件 → std::remove → 返回 200。目录和其他类型禁止删除；不存在返回 404。这是路径和方法限制，不是用户身份验证。

errorResponse 先查 server.error_pages，能打开自定义文件则使用它，否则用 text/plain 的默认错误说明。methodNotAllowed 在错误响应上额外加 Allow。handleError 是错误码分发器，并不是支持所有 HttpStatus 的完整映射；未列出的值进入 500 兜底。

## 9. CGI：不是 C++ 函数调用，而是启动另一个程序

### 9.1 启动与管道

```text
Server::tryStartCgi → findCgiExecutable（按扩展名找解释器）
                   → buildPath → startCgi
                     → new CgiHandler → CgiHandler::start

父进程 webserv                          CGI 子进程
request.body
    ↓ swap
_requestBody → write(inputPipe[1]) ──→ inputPipe[0] → dup2 → stdin(0)
                                                          ↓ 程序执行
_output ← read(outputPipe[0]) ←────── outputPipe[1] ← dup2 ← stdout(1)
stderr(2) 没有重定向，通常仍连接启动 webserv 的终端
```

start 先创建两组 pipe，构建环境变量，设置父进程使用的两端为非阻塞，再 swap 请求正文，随后 fork。环境中的 CONTENT_LENGTH 必须在 swap 清空 request body 之前计算。

子进程关闭不用的两端，dup2 到 0 和 1，关闭 Server 提供的多余 fd，chdir 到脚本目录，再 execve(解释器, argv, envp)。argv[1] 使用脚本文件名。execve 成功会替换子进程程序，不会返回；失败才清理 envp 并 _exit(1)。

父进程关闭自己不用的两端，保留输入写端和输出读端。Server 把两端登记到 _cgiFds 和 _pollFds，并暂停客户端正常收发。

### 9.2 环境变量

| 变量 | 当前来源 |
| --- | --- |
| GATEWAY_INTERFACE | 固定 CGI/1.1 |
| REDIRECT_STATUS | 固定 200，用于 CGI 兼容 |
| REQUEST_METHOD / SERVER_PROTOCOL | request.method / version |
| REQUEST_URI | 解码后的 path，若 query 非空则拼上 ?query |
| QUERY_STRING | query 原字符串 |
| SCRIPT_NAME / PATH_INFO | 当前都使用完整 request.path |
| SCRIPT_FILENAME | buildPath 的结果，可能是相对路径 |
| CONTENT_TYPE | content-type 请求头 |
| CONTENT_LENGTH | 已解析正文的实际字节数，chunked 解码后也能计算 |
| SERVER_NAME / SERVER_PORT | accept 时得到的服务器地址字符串和监听端口 |
| REMOTE_ADDR | 客户端 IPv4 地址 |
| HTTP_XXX | 其他请求头名称转大写，- 变 _，增加 HTTP_ 前缀 |

例如 Cookie → HTTP_COOKIE；X-Test → HTTP_X_TEST。CONTENT_TYPE 和 CONTENT_LENGTH 不再作为 HTTP_XXX 重复生成。当前 PATH_INFO 没有严格拆成“脚本路径之后的额外路径”，REQUEST_URI 也没有保留原始编码；复习时不要把这些兼容性简化讲成完整 CGI 标准。

### 9.3 读写与完成条件

writeBody 只写当前剩余正文，使用 _bodyOffset 记录进度；写完 closeInput，向 CGI 表达 stdin EOF，并释放正文缓冲。

readOutput 每次读取 4096 字节并累积。读到 0 关闭输出；输出总量超过 128 MiB 或 I/O 出错则标记失败。当前是“收完整 CGI 输出后再回复客户端”，不是流式 CGI。

stdout EOF 表示没有更多输出，但不表示 waitpid 已回收子进程。handleCgiRead 在 EOF 后尝试 waitForChild；还没退出就交给下一轮 checkCgiChildren。正常完成需要输出关闭且子进程被确认结束。

isChildSuccess 检查：确认子进程已结束、没有 I/O 失败、正常 exit 且退出码为 0。非零退出或信号终止进入 500 路径。

### 9.4 CGI 输出如何变成 HTTP 响应

finishCgi → swapOutput → buildCgiResponse → swapWriteBuffer → 客户端 POLLOUT。

buildCgiResponse 在同一个字符串上修改：识别 CRLFCRLF 或 LFLF 分隔符；读取 Status 转成 HTTP 状态行；保留普通 CGI 头；丢弃 CGI 的 Content-Length、Connection、Transfer-Encoding；按实际 body 字节数补 Content-Length；按 state.keepAlive 补 Connection。最后删除原 CGI 头并插入 HTTP 头。

没有头分隔符时，当前代码把整个输出当正文，默认 text/html 和 200。这是项目兼容策略。

丢弃 Transfer-Encoding 不等于解码了 chunked；当前代码并没有对 CGI 的 chunked 输出做解码。讲解时应当说明 CGI 应输出普通正文，由服务器管理 HTTP 消息长度。

### 9.5 清理的三个不同动作

1. closeInput / closeOutput：关闭内核 fd，更新 CgiHandler 的 fd 与开关状态。
2. _cgiFds.erase / removePollFd：移除服务器的查找索引和事件登记。
3. removeCgi：移除任务并 delete 对象；析构负责子进程与尚未关闭的管道。

只 close 不移除事件登记会留下过期 fd；只 erase 不 close 会泄漏内核资源。closeOutput 会把保存的 fd 设为 -1，错误回调还要用传进来的原始 fd 删除登记，这就是之前额外清理的原因。

## 10. 响应发送、keep-alive 与 pipelining

普通响应：HttpResponse → getResponse 生成字符串 → queueResponse → Client.swapWriteBuffer。CGI 响应走 finishCgi 的独立组装路径，然后汇合到同一个 writeBuffer。

handleWrite 使用 writeBuffer.c_str() + bytesSent 开始发送。send 返回的正数只表示这次交给系统的字节数，不能假定一次发完。发送后更新偏移和活动时间。

全部发完后：keepAlive 为 false 则 removeClient；为 true 则释放 writeBuffer、重置发送偏移和 RequestState。readBuffer 已经含下一条请求时，直接再次 processRequest；否则等待 POLLIN。

consumeReadBuffer(state.pos) 只去掉当前请求占用的字节，保留下一条请求。因此两个请求可以一次 recv 进来，但当前实现仍按请求顺序生成和发送响应，没有让同一连接中的请求并行执行。

## 11. 超时、退出和大内存

client 的活动时间在接收正数字节、排队新响应、发送正数字节、重置请求状态时更新。查询 getter 或每次 poll 醒来不更新时间，否则无活动连接永远不超时。

CGI 的 5 秒是管道无成功读写活动的时间；成功输入或输出都会刷新。持续计算但无输出的 infinite.py 会超时。client 的 30 秒检查跳过 events=0 的 CGI 等待阶段。

SIGINT → handleSignal → g_running=0 → run 结束 → Server 析构。SIGPIPE 被忽略后，向断开的连接/管道写入可由返回值错误处理，不会因为这个信号直接终止服务器。

大请求的数据流：

```text
客户端 readBuffer → HttpRequest.body（完整正文复制）
请求完整后释放已消费的 readBuffer
HttpRequest.body ─swap→ CgiHandler._requestBody
写入 CGI 完成后释放 _requestBody
CGI stdout → CgiHandler._output（累积完整输出）
_output ─swap→ 临时 response ─原地改头─swap→ Client.writeBuffer
发送完成后释放 writeBuffer
```

swap 降低某些交接点的复制成本，但没有消除最初的正文复制、CGI 输入输出重叠、并发任务和子进程内存。所以 20 个 100 MB 请求不能简单理解为只占 2 GB。内存释放到分配器后，系统监控值也不一定立即等比例下降。

## 12. Bonus 与测试代码的归属

cookie.py 从 HTTP_COOKIE 读取 Cookie，必要时输出 Set-Cookie。session.py 校验 Session ID、建立 session_data、清理过期文件、读取并增加访问次数，再输出响应。计数存服务器文件，浏览器只保存随机 ID。

Session 过期清理在下一次执行脚本时触发，没有后台定时线程。同一个 Session 的并发更新目前没有文件锁，也不是事务。

hello.py / hello.sh 验证多解释器及环境变量；post.py 演示读 stdin；relative.py 验证工作目录；status.py 验证 Status；content_length.py 验证响应长度；error.py 验证非零退出；infinite.py 验证无活动超时。

my_testers 是独立的客户端程序，不会被 webserv 的 main 调用。线程池、socket.sendall、http.client.HTTPConnection 等属于测试器知识，不代表服务器自身采用线程池。外部 tester 和 cgi_tester 只有可执行文件，不能仅凭仓库阅读列出其内部函数。

## 13. 当前实现与容易记错的地方

这里是阅读边界提醒，不是宣称已经重新完成一次完整漏洞审计。

1. Server 超过 1000 行主要因为同时承担网络事件调度、请求流程协调、CGI 事件适配与响应规范化；从职责上可拆分，但现在应先按这些职责理解，不必先重构才能复习。
2. RequestHandler::getRoot 当前没有发现运行路径中的调用；buildPath 直接取配置 root。函数存在不代表参与主流程。
3. Client::getFd、CgiHandler::getPid，以及 const 版本 Client::getRequestState 等是否被调用，以函数索引标注的直接调用记录为准；无调用不等于必须删除。
4. 普通文件 I/O 和完整响应缓冲不是严格全程非阻塞或恒定内存。
5. 当前没有 Host 虚拟主机、完整 PATH_INFO 拆分、chunk extension/trailer 支持，也没有上传事务或 Session 文件锁。
6. hasParentTraversal 检查路径段 ..，isSafeFilename 检查上传文件名；这不自动解决符号链接逃出根目录或 stat 与写入之间的竞态。
7. htmlEscape 的双引号分支目前写的是 &quot，少了分号；正确 HTML 实体写法应为 &quot;。笔记保留当前事实，未替你改代码。
8. Server 析构会在 CGI 析构后再遍历 poll fd；要结合关闭顺序思考重复 close，而不是背诵“RAII 自动保证全部资源没问题”。
9. 旧测试脚本的标题可能与最新配置不一致。例如默认 /upload 只允许 POST，普通 POST 也不走 upload_store。测试注释不能替代实际配置和 handler 的行为。
10. 本地 README 写 Fedora 是目标环境；本次没有在 Fedora 上实测，不能据此新增“已验证 Fedora”的结论。

## 14. 复习顺序与自测

建议顺序：main → 配置解析与验证 → Server.run → Client/RequestState → RequestParser → RequestHandler → HttpResponse → CgiHandler → CGI 回调与清理 → Cookie/Session → Makefile/测试。

1. 为什么 recv 一次不能假设得到一个完整请求？答：TCP 是字节流，必须依赖 HTTP 长度与分隔规则。
2. RequestParser 临时对象销毁后，解析进度在哪里？答：Client 内的 RequestState。
3. 为什么请求行必须早于 body 上限选择？答：路径决定 location，location 可覆盖 server 限制。
4. configValidator 能替代 preCheck 吗？答：前者检查启动配置，后者检查实际请求。
5. 一个 CGI 为什么要两根 pipe？答：stdin 输入与 stdout 输出需要两个方向。
6. CGI stdout EOF 后能马上宣布成功吗？答：还要 waitpid 确认退出状态，并检查 I/O 失败。
7. removePollFd 为什么不等于 close？答：前者只改用户态登记，后者释放内核描述符。
8. 为什么 CGI Traceback 出现在服务器终端？答：stderr 继承，没被 stdout 管道重定向。
9. 为什么有了 swap 仍可能 OOM？答：仍有完整正文、输出、并发任务和子进程等内存。
10. 为什么 keep-alive 后要保留 readBuffer？答：可能已经收到下一条请求。
11. Session 数据为何能跨 CGI 进程保存？答：持久文件保存状态，Cookie ID 用于定位。
12. 为什么改 .hpp 后能自动重编译？答：-MMD 生成 .d，-include 将头文件依赖读入 Makefile。

能把这 12 个问题各用自己的话讲清楚，再对照函数索引定位实现，才算把整体关系真正串起来。
